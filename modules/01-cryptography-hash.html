Module 01 · Start with the tools

Cryptography and hash structures

Cryptography gives a system ways to keep information private, detect changes, and check authorization. A blockchain combines these tools with shared rules; none of the tools alone creates a blockchain.

1. Start from the security goal

Imagine Alice sends Bob the instruction “transfer 10 credits to Ravi.” We can ask several different questions: can another person read it; can someone alter the amount; can Bob tell who sent it; can Alice later deny authorizing it? These are different security goals, so they need different mechanisms.

Goal (use your lecture’s exact labels)Question it answersTool that can help
ConfidentialityCan an unauthorized reader understand the message?Encryption
IntegrityCan the receiver detect an unauthorized change?Hash, MAC, or signature, depending on what is trusted
AuthenticationCan the receiver check who or what authorized the message?MAC for shared-key parties; signature for public verification
Non-repudiation / accountabilityCan a third party verify a signature associated with a key?Digital signature plus a trustworthy identity-to-key binding
Keep integrity and authenticity separate.A plain hash can reveal that a message differs from a known digest. If an attacker can replace both the message and its digest, the hash alone does not tell you who created either one.

2. Symmetric and asymmetric encryption

Symmetric encryption uses a shared secret key to encrypt and decrypt. It is efficient for large amounts of data, but Alice and Bob need a safe way to share and protect the key.

Asymmetric encryption uses a related public and private key. For confidentiality, Alice can encrypt to Bob’s public key and Bob uses his private key to decrypt. The public key can be shared; the private key must remain secret. In practice, asymmetric techniques often help establish a shared session key, while symmetric encryption protects the bulk data.

QuestionSymmetricAsymmetric

StrengthFast for bulk encryptionSupports public-key distribution and signatures

Important distinctionSigning is not the same operation as public-key encryption. A signer uses a private key to create a signature; verifiers use the corresponding public key to check it. A signature does not hide the message.

3. Hash functions

A cryptographic hash takes an input of any practical length and produces a fixed-length digest. Write this as H(message) = digest. The same bytes produce the same digest, which makes a hash useful as a compact fingerprint.

Security properties to know

  • Preimage resistance: given a digest, it should be infeasible to find an input that hashes to it.
  • Second-preimage resistance: given a particular input, it should be infeasible to find a different input with the same digest.
  • Collision resistance: it should be infeasible to find any two different inputs with the same digest.
  • Avalanche effect: a small change in input changes many digest bits unpredictably. This is a useful design behavior, not a replacement name for collision resistance.

SHA is a family of standardized hash algorithms. Bitcoin uses SHA-256 in its proof-of-work process, with the protocol’s precise serialization and hashing rules. A digest is not encryption: it is not designed to be reversed to recover the original message.

4. MACs and digital signatures

A message authentication code (MAC) is computed from a message and a shared secret. A recipient with that secret can check that the message matches the MAC and that it came from someone who knows the shared key. Because both parties know the key, an outside observer cannot use a MAC to identify which one created it.

A digital signature is created with the signer’s private key and checked with a corresponding public key. It supports integrity and public verification under that key. To connect the key to a named person, a system also needs a trustworthy way to bind that identity to the public key.

5. Hash pointers and Merkle trees

A hash pointer refers to data and includes a hash of that data. If the data changes, its digest changes, so a later reader can detect the mismatch. Linking records this way makes tampering evident; it does not prevent someone from changing a local copy.

A Merkle tree hashes records at the leaves, then hashes pairs of child digests upward until one root remains. A block can commit to many transactions with this single Merkle root.

For a large tree, a membership proof contains only the sibling digest at each level. The verifier recomputes the path to the root rather than downloading every transaction. The root proves inclusion in the committed set; it does not prove that the transaction is truthful or valid by itself.

6. Merkle–Damgård, sponge, and length extension

Merkle–Damgård is a design pattern that processes padded input in fixed-size blocks, repeatedly updating a chaining state. Many familiar SHA-2 hashes use this general construction. Sponge hashes absorb input into a larger internal state and then squeeze output from it; SHA-3 is based on a sponge construction.

The construction matters when someone invents a MAC. In a naive prefix construction H(secret || message), certain Merkle–Damgård hashes expose a final state that lets an attacker continue hashing an extended message, if the attacker can estimate the secret length. The attacker may produce a digest for an extended string without learning the secret. This is the length-extension attack.

What the attack does not meanIt does not mean that the attacker recovered the secret or found a collision. It shows that the particular “secret concatenated with message” construction is unsafe. Use a vetted MAC construction rather than designing one yourself.

Quick check

Why does a hash not provide confidentiality?

A hash is a digest, not an encryption scheme. It does not hide the message; small or guessable messages may even be tested by hashing guesses.

Can a MAC provide public non-repudiation?

No. Every holder of the shared key can create a valid MAC, so an outside verifier cannot tell which holder generated it.

What does a Merkle proof establish?

It establishes that a leaf can be combined with the supplied sibling hashes to reach the trusted root. It does not establish the real-world truth of the leaf’s contents.

What is the essential length-extension lesson?

Do not treat H(secret || message) as a safe MAC for a Merkle–Damgård hash. A continuation attack can create a valid digest for an extended message without revealing the secret.

Exam-ready summary

  • Choose a tool based on the security goal.
  • State whether a mechanism uses a key and who can verify it.
  • Explain hash properties in terms of an attacker’s task.
  • Draw four leaves to explain a Merkle root and membership path.
  • Describe length extension as a flaw in a naive keyed construction.
